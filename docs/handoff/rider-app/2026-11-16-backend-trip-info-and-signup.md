## 11. 라이더 지원센터 — 답변·대화·배송 밖 문의
사용자 요청 2026-11-16: "도움요청은 지원센터 화면이 뜨게 해야 하는 거 아니야? 백오피스 지원센터랑 연결되게."

- 계약에 없어 못 한 것(요청):
  1. 상담원 답변을 라이더가 보기 — 지금 `resolutionNote` 는 직원에게만. 라이더에게 보여 줄 답변 칸(또는 사건 메모 중 라이더 공개분)이 필요하다.

  4. 배송과 상관없는 문의(정산·계정·앱 오류 등) — 지금 도움요청은 배송 ID 가 있어야 한다.
  5. 처리 결과 알림(푸시, BR-09) — 지금은 화면에 들어오거나 "다시 확인"을 눌러야 바뀐다.

## 12. 거주지 주소 — 서버에서도 실제 주소만 받기 (2026-11-17 추가)

- 빈틈: 지금 계약(`RiderSignupRequest.residence` · `RiderProfileUpdate.residence`)은 `roadAddress` 가 아무 문자열이다. 앱을 거치지 않은 요청이면 지어낸 주소도 들어간다.
- 요청(하나를 골라 주면 앱이 맞춘다):
  1. 서버가 `roadAddress` 를 주소 정본(행안부 도로명주소 API, 카카오 로컬 주소 검색 등)으로 확인하고, 없는 주소는 422(예: `INVALID_ADDRESS`)로 거절.

- 프로필에서 주소를 바꿀 때(`PATCH /riders/me`)도 같은 규칙이 필요하다. 주소는 개인정보라 로그·이벤트에 원문을 남기지 않는다(앱도 남기지 않음).

## 13. 전달 불가 등록과 지원센터 대화 묶기 (2026-11-17 추가)
사용자 지적 2026-11-17: 전달 불가를 알리면 상담원과 대화할 수 없고, 같은 내용으로 도움요청을 또 보내야 대화가 열린다.
- 앱(반영): 전달 불가(`POST …/failures`)가 등록되면 같은 내용으로 도움요청(`POST …/help-requests` — 유형은 사유에 맞춤, 내용 "전달 불가를 알렸어요 · 사유: …", 증빙 photoRef)을 자동으로 보내고 그 대화 화면으로 간다.
- 그래서 운영자 쪽에는 전달 실패 대기(`GET /deliveries?state=FAILURE_REPORTED`)와 RIDER_HELP 사건이 따로 하나씩 생긴다.
- 물음:
  1. 둘을 한 건으로 볼 수 있게 연결해 줄 수 있는가? 예: 도움요청에 실패 등록 참조를 받기, 또는 실패 등록 응답에 연결된 도움요청 ID 를 주기.
  2. 아니면 실패 등록 자체가 지원센터 사건과 대화를 열게 바꿔 줄 수 있는가? 그러면 앱은 도움요청을 따로 보내지 않는다.
  3. 전달 재개(사용자 지적 2026-11-17 — 알린 뒤 고객과 다시 연락돼 전달할 수 있게 되는 경우): 지금은 라이더가 취소할 수 없고, 운영자가 반려(`failure-decisions` REJECT)해야 돌아간다. 앱은 "고객과 다시 연락이 됐어요. 전달할 수 있어요 — 전달 불가를 반려해 주세요."를 대화 메시지로 보내고, 배송 상태를 8초마다 다시 확인한다. 다음 둘 중 하나가 있으면 상담원이 놓치지 않는다.
     - 라이더의 "전달 재개 요청"을 구조화된 값으로 보내기. 예: `POST …/failures/withdrawal-requests`, 또는 사건함에 표시되는 플래그.
     - 운영자 대기 목록에 그 요청 표시하기.
     반려 결과는 지금처럼 `GET /deliveries/{id}` 상태로 확인한다(푸시 BR-09 가 생기면 그것으로).

- 빈틈: 계약에 가입 전 계좌 확인 API 가 없다. 가입·프로필 변경 때 같은 계좌를 막는 규칙(409)도 계약에 적혀 있지 않다.
- 요청:
  1. 같은 계좌를 여러 라이더가 등록하지 못하게 할지 정책을 정해 달라(사용자 요청은 중복 불가).
  2. 정해지면 `POST /riders/account-checks` `{ bankCode, accountNumber }` → `{ available }`. 라이더 토큰으로 호출하고, 번호는 저장·로그하지 않는다.
  3. 가입(`POST /riders/signups`)·프로필 변경(`PATCH /riders/me`) 때도 다시 검사해서 409(예: `DUPLICATE_ACCOUNT`)로 거절.

## 16. 회신(2026-11-16~17) 반영 뒤 남은 물음 (2026-11-17 추가)
앱이 붙인 것은 다음과 같다(실서버 모드 코드, 시험은 가짜 응답으로만 — 서버는 아직 부르지 않았다).
- 도움요청 대화 messages
- 내 도움요청 목록
- 면허 확인 license-checks

3. ~~**가입 `deliveryAreas[].mfcId`**~~ — 2026-11-17 해결: 앱이 `GET /mfc-pickup-points` 의 centerId 를 쓴다(생성기에 center-master 추가, PC 1 알림 `2026-11-17-pc1-gen-rider-auth-center-master.md`). 이전 내용: 서버 CenterId 여야 하는데, 앱은 아직 앱 지점표 코드(`MFC-BSJ-01` 등)를 쓴다. 지점 목록 `GET /mfc-pickup-points` 를 붙이려면 center-master 생성 클라이언트가 필요하다. `tools/gen_api.dart` 서비스 목록에 center-master-service 를 rider 로 더하는 일은 PC 1 몫이다. LAN 에 부산진구지점만 등록돼 있다는 것도 확인했다.
4. 수락 뒤 예정 시각: 회신대로 "수락 직전 제안의 pickupEtaSeconds·dropEtaSeconds" 로 계산한다(앱을 다시 켜면 이 값이 없어 예정 시각을 표시하지 않는다). 배송 조회에 서버 계산 예정 시각을 넣어 줄 수 있는가.

## 17. 라이더 계정 탈퇴 — LAN 서버 501 (2026-11-17 추가)
- 앱이 계약대로 `POST /api/v1/riders/me/withdrawals` 를 부르면 LAN 에서 **501** 이 온다(실기기 3회, rid 32d0cfd8…·29643ed4…·f1e53cfc…). rider-service 에 탈퇴 처리 코드가 없다(계약만 있음).
- 요청:
  - 계약대로 구현해 달라. 진행 중 배송·미정산 수행료·제한 조사 중이면 409 INVALID_STATE. 결과는 `GET …/withdrawals/{requestId}`(PENDING·COMPLETED·REJECTED + blockers).
  - `blockers` 값 목록도 계약에 적어 달라. 앱은 지금 글자로 대략 나눈다(DELIVER·SETTLE/EARNING/PAY·RESTRICT/REVIEW).
  - 탈퇴가 끝나면 rider-auth 세션·토큰도 끊기는지 알려 달라.
- 앱(반영): 501 이면 "결과를 모름 — 다시 눌러" 대신 "지금은 앱에서 탈퇴를 처리할 수 없어요(서버 준비 중)"로 안내한다. 서버가 완료(COMPLETED)를 확정했을 때만 로그아웃한다.

## 19. 배송 밖 실시간 채팅 상담 (2026-11-17 추가)
- 사용자 요청: "마이페이지 지원센터 문의에 실시간 채팅 상담도 있었으면."
- 지금 계약에서 배송 밖 문의(case `/inquiries`)는 라이더가 한 번 남기면 지원센터(RIDER_OPS)가 `replies` 로 답하는 방식뿐이다. 라이더가 이어 쓰는 경로가 없어서 채팅이 안 된다. 배송 건 대화(`/deliveries/{id}/help-requests/{id}/messages`)는 배송 ID 가 있어야 한다.
- 앱(목으로 반영): 지원센터 문의 맨 위에 "실시간 채팅 상담" → 대화 화면(3초마다 확인, 같은 키 재전송은 같은 메시지). 실서버는 "준비 중 — 문의를 남겨 주세요"로 안내한다.
- 요청(둘 중 하나):
  1. 문의 한 건에 딸린 메시지: `GET/POST /inquiries/{inquiryId}/messages`(라이더 본인 + RIDER_OPS, `after` seq, 닫힌 문의는 409). 도움요청 대화와 같은 모양이다.
  2. 문의 없이 여는 상담 세션: `POST /rider-support/chats` → `{chatId}` + 같은 메시지 API. 상담원 배정·대기 순서·운영 시간 밖 안내를 포함한다.
- 상담원 쪽 화면(백오피스, PC 2)과 새 메시지 알림(알림함 CASE)도 함께 필요하다.
